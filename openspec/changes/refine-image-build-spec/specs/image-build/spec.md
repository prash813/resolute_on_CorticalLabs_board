# Spec Delta

## MODIFIED Requirements

### Requirement: Cross-built classic server image
The image SHALL be built for arm64 on an x86_64 host with `ubuntu-image classic`, from `classic/resolute/ubuntu-server-kria.yaml` in `xlnx-image-definitions` on branch `kria-resolute` (tracking `origin/kria-resolute-definition`). The build SHALL run from the repository root with work directory `work` and output directory `out`.

#### Scenario: Building the image
- **WHEN** the developer runs `sudo ubuntu-image classic --debug -w work -O out classic/resolute/ubuntu-server-kria.yaml` from the `xlnx-image-definitions` root
- **THEN** the build completes without error and writes `out/kria-server.img`, `out/kria-server-rootfs.tar.gz` and `out/kria-server.manifest`

#### Scenario: Wrong branch
- **WHEN** the checked-out branch has no `classic/resolute/ubuntu-server-kria.yaml`
- **THEN** the build is not started, and the developer checks out `kria-resolute` from `origin/kria-resolute-definition`

### Requirement: Package sources
The image definition SHALL add exactly these extra PPAs, each with `keep-enabled: false` and a pinned signing-key fingerprint: `ubuntu-xilinx/default` (OEM meta packages), `kkaniewski/linux-amd-embedded` (kernel) and `sinan-k/xlnx-flash-kernel` (flash-kernel). The rootfs SHALL come from `http://ports.ubuntu.com/ubuntu-ports/`, series `resolute`, pocket `updates`.

#### Scenario: Patched flash-kernel present
- **WHEN** the image is built
- **THEN** the installed flash-kernel is the `sinan-k/xlnx-flash-kernel` version, its `all.db` maps `ZynqMP *K26*` (flavor `amd-embedded`) to `Boot-ITS-File-Name: image-kria.its`, and it ships `/usr/share/flash-kernel/its/image-kria.its`

#### Scenario: PPAs used for a local build
- **WHEN** the image definition is inspected
- **THEN** `customization.extra-ppas` lists `ubuntu-xilinx/default` (`803DDF595EA7B6644F9B96B752150A179A9E84C9`), `kkaniewski/linux-amd-embedded` (`2A62D5777A3432169DCAAF75E299459FD7C254FE`) and `sinan-k/xlnx-flash-kernel` (`B51FAEACB53E5AE8F9A89571C54C7DDAF634E510`), all with `keep-enabled: false`

#### Scenario: Private limerick-team PPAs not needed locally
- **WHEN** the image is built on a developer host without `limerick-team/limerick-proposed` or `limerick-team/limerick-updates` credentials
- **THEN** the build still succeeds, because only CI adds those PPAs (through `images.yaml` `extra_ppas` with tokens)

#### Scenario: PPAs not left enabled in the image
- **WHEN** `/etc/apt/sources.list.d` in the built rootfs is inspected
- **THEN** none of the three extra PPAs is enabled

#### Scenario: Known-good package versions
- **WHEN** `out/kria-server.manifest` is read
- **THEN** it lists `flash-kernel 3.110ubuntu2.5`, `linux-image-7.0.0-1001-amd-embedded 7.0.0-1001.1`, `oem-limerick-meta 0.18~xlnx01` and `oem-limerick-kria-meta 0.22`, or newer versions that are recorded with a KV260 boot result

### Requirement: FIT image generation
flash-kernel SHALL generate `image.fit` and `boot.scr.uimg` in the rootfs `/boot/firmware` during the build, from `image-kria.its` and `bootscr.zynqmp.kria` (machine `ZynqMP *K26*`). The hook `hooks/kria/classic/10-flash-kernel-fitimage <output-dir>` SHALL then move both files to partition 1 and SHALL NOT regenerate the FIT.

#### Scenario: FIT regenerated after the build
- **WHEN** the developer runs the hook `hooks/kria/classic/10-flash-kernel-fitimage out` on the build output
- **THEN** the FIT already generated by flash-kernel in the chroot is placed on the boot partition without being rebuilt, so its kernel, ramdisk and DTB hashes match the rootfs-generated FIT, and it has a configuration for each supported board

#### Scenario: Running the FIT hook
- **WHEN** the developer runs `sudo bash hooks/kria/classic/10-flash-kernel-fitimage out` from the `xlnx-image-definitions` root after the build
- **THEN** partition 1 of `out/kria-server.img` contains `image.fit` and `boot.scr.uimg`, the rootfs `/boot/firmware` no longer contains them, and `work/` has been removed

#### Scenario: Hook run without the output directory
- **WHEN** the hook is run without an argument, or with a directory that contains no `*.img`
- **THEN** it prints `No image file found in <dir>`, exits non-zero and leaves the image unchanged

#### Scenario: FIT contents
- **WHEN** the moved `image.fit` is listed with `dumpimage -l`
- **THEN** it contains `kernel-1`, `ramdisk-1` and the DTB images `zynqmp-smk-k26-revA`, `smk-k26-revA-sck-kr-g-revA`, `smk-k26-revA-sck-kv-g-revA`, `smk-k26-revA-sck-kr-g-revB`, `smk-k26-revA-sck-kv-g-revB` and `smk-k24-revA-sck-kd-g-revA`
- **AND** it contains the configurations `conf-zynqmp-smk-k26-revA` (default), `conf-zynqmp-smk-kd-g-revA`, `conf-smk-k26-revA-sck-kr-g-revA`, `conf-smk-k26-revA-sck-kv-g-revA`, `conf-smk-k26-revA-sck-kr-g-revB` and `conf-smk-k26-revA-sck-kv-g-revB`

### Requirement: Kernel node describes the PE kernel correctly
Because the distro kernel is an EFI zboot PE application (EFI stub plus zstd-compressed arm64 Image), the `kernel-1` node of the FIT used with BSP 2026.1 firmware SHALL use `os = "efi"` and `compression = "none"`, and SHALL keep `type = "kernel"`, `arch = "arm64"` and load/entry `0x00200000`.

#### Scenario: KV260 FIT
- **WHEN** the FIT for KV260 is inspected with `dumpimage -l`
- **THEN** `kernel-1` is reported with `Compression: uncompressed`, `OS: EFI Firmware`, `Architecture: AArch64` and load/entry address `0x00200000`

#### Scenario: Kernel payload is the unmodified PE
- **WHEN** `kernel-1` is extracted with `dumpimage -T flat_dt -p 0 -o kernel image.fit`
- **THEN** `file kernel` reports `PE32+ executable (EFI application) Aarch64` and the bytes are identical to `/boot/vmlinuz-<version>` from the rootfs

#### Scenario: Mislabelled kernel node
- **WHEN** `kernel-1` reports `gzip compressed` / `OS: Linux`
- **THEN** the image does not meet this requirement: KV260 U-Boot fails with `Bad gzipped data`, and the image has to be rebuilt with the `.its` patch or fixed with the post-build relabel

## ADDED Requirements

### Requirement: Build host prerequisites
The build host SHALL be x86_64 Ubuntu with about 30 GB free disk, the `ubuntu-image` snap (classic confinement), and the debs `qemu-user-static`, `binfmt-support`, `device-tree-compiler` and `u-boot-tools`, so that arm64 chroot steps can run and FIT images can be inspected and edited.

#### Scenario: Host tools present
- **WHEN** the developer checks the host before building
- **THEN** `ubuntu-image`, `dumpimage`, `mkimage`, `fdtget` and `fdtput` are on `PATH`, and the binfmt handler for `qemu-aarch64` is registered

### Requirement: Build-time .its patch for the zboot PE kernel
Before running flash-kernel in the chroot, `classic/resolute/10-run-flash-kernel.sh` SHALL change only the `kernel-1` node of `/usr/share/flash-kernel/its/image-kria.its` to `os = "efi"` and `compression = "none"`. It SHALL leave every other node unchanged, be idempotent, and fail the build if the expected text is missing.

#### Scenario: Patched template produces a correct FIT
- **WHEN** the image is built with the patched `10-run-flash-kernel.sh`
- **THEN** the `image.fit` written by flash-kernel already meets "Kernel node describes the PE kernel correctly" without any post-build edit

#### Scenario: Other nodes untouched
- **WHEN** the patched `image-kria.its` in the rootfs is compared with the one shipped by the flash-kernel package
- **THEN** the only differences are the `os` and `compression` lines of `kernel-1`, and `ramdisk-1` still has `os = "linux"` and `compression = "none"`

#### Scenario: Template already fixed upstream
- **WHEN** the installed `image-kria.its` already has `os = "efi"` and `compression = "none"` in `kernel-1`
- **THEN** the script leaves it as is and the build continues

#### Scenario: Template layout changed
- **WHEN** the `kernel-1` node has neither the `linux`/`gzip` values nor the `efi`/`none` values
- **THEN** the script exits non-zero with a message naming `image-kria.its`, and the build fails instead of producing an unbootable FIT

#### Scenario: Change delivered as a patch
- **WHEN** the `.its` change is reviewed
- **THEN** it exists as a `git format-patch` file against `xlnx-image-definitions` branch `kria-resolute`, with an explanatory commit message and a `Signed-off-by` trailer

### Requirement: Post-build FIT relabel as recovery
For an image built without the `.its` patch, the developer SHALL be able to fix `image.fit` on partition 1 of `out/kria-server.img` after the hook has run. This is done with `fdtput -t s image.fit /images/kernel-1 os efi` and `fdtput -t s image.fit /images/kernel-1 compression none`, keeping a copy of the original FIT.

#### Scenario: Relabelling an unpatched image
- **WHEN** the developer loop-mounts partition 1, copies `image.fit` to `image.fit.orig`, applies both `fdtput` edits to a copy and writes it back
- **THEN** `fdtget image.fit /images/kernel-1 os` prints `efi`, `fdtget image.fit /images/kernel-1 compression` prints `none`, and the kernel hash in the FIT still verifies

### Requirement: Disk image layout
`out/kria-server.img` SHALL use an MBR partition table. Partition 1 SHALL be bootable, FAT32 (type `c`), labelled `system-boot`, starting at sector 2048 with a size of 1 GiB (2097152 sectors). Partition 2 SHALL be ext4, labelled `writable`, and fill the rest of the image.

#### Scenario: Inspecting the partition table
- **WHEN** `sfdisk -d out/kria-server.img` is run
- **THEN** it reports `label: dos`, partition 1 at `start=2048, size=2097152, type=c, bootable` and partition 2 starting at sector 2099200 with `type=83`

#### Scenario: Mount labels match fstab and boot script
- **WHEN** the image boots on KV260
- **THEN** `/` is mounted from `LABEL=writable` and `/boot/firmware` from `LABEL=system-boot`, matching the image definition's fstab and the `root=LABEL=writable` set by `boot.scr.uimg`

### Requirement: Boot script selects the KV260 configuration
The `boot.scr.uimg` on partition 1 SHALL select the FIT configuration from the carrier card EEPROM. For an `SCK-KV-G` card at revision B, 1 or 2, or an unknown revision, it SHALL pick `#conf-smk-k26-revA-sck-kv-g-revB`, set `console=ttyPS1,115200` and `root=LABEL=writable`, and start the kernel with `bootm`.

#### Scenario: KV260 rev B boot
- **WHEN** a KV260 with an `SCK-KV-G` rev B carrier boots the image while serial output on `ttyPS1` at 115200 is captured
- **THEN** the log shows `Kria DT: #conf-smk-k26-revA-sck-kv-g-revB`, U-Boot starts the kernel through the EFI loader, and the system reaches a login prompt
